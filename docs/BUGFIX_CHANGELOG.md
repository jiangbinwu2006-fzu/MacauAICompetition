# 澳门文旅智联缺陷修复日志

更新时间：2026-07-27

## 本轮用户反馈

### BUG-01 偏好设置后生成路线无法重置

- 现象：路线生成后只有重新生成、撤回和恢复原始路线，没有清空当前路线的操作。
- 根因：后端已有 `DELETE /api/trips/current`，前端 API 和行程工具栏没有接入。
- 修复：新增清空路线按钮，清除后端会话行程、前端行程状态、地图线路、公交详情和弹窗状态。
- 状态：已完成；前端生产构建通过，后端重置接口已存在并由会话接口契约覆盖。

### BUG-02 公交路线缺少高德智能规划详情

- 现象：公交方案只有概要指标和地图路线，没有说明乘坐线路、上车站、下车站及站点位置。
- 根因：高德 `AMap.Transfer` 使用 `extensions: base`，且回调结果未解析。
- 修复：切换为完整公交结果，解析公交线路、上车站、下车站、途经站、耗时及站点坐标；上下车站以不同颜色图标标记在地图，并同步显示在行程面板。
- 状态：已完成；前端生产构建通过。实际线路、站名与坐标由运行时高德在线结果决定，高德无结果时继续使用静态降级路线。

### BUG-03 后端频繁自动关闭

- 现象：前端偶发显示点位读取失败，检查发现 `8290` 后端进程已退出。
- 根因：开发服务曾通过临时命令父进程启动，父进程结束时 Java 子进程被一并终止；后端日志没有 Spring Boot 崩溃异常。
- 修复：新增独立隐藏进程启动器和后端守护脚本；异常退出 3 秒后自动重启，PID 与输出统一记录到 `.runtime`；新增配套停止脚本。
- 状态：已完成并验证。测试中强制结束后端 PID `13944`，守护器自动启动新 PID `41612`，`8290` 恢复监听且目录接口返回 60 条点位。

### BUG-04 运营测试系统区域与布局问题

- 现象：区域只能从固定值中选择，页面控制区偏窄；场馆关闭没有清晰的场馆选择流程。
- 修复：区域字段改为可选择也可自由输入；桌面端使用明确的左侧测试参数、右侧事件结果布局并扩大页面有效宽度；选择“场馆关闭”时自动筛选场馆类点位并显示“选择关闭场馆”。
- 状态：已完成；Vue 模板编译与生产构建通过，区域输入、条件点位筛选和左右布局均已进入构建产物。

### BUG-05 后端重启后偏好显示保存失败

- 现象：后端重启后点位可以读取，但当前页面保存或重置偏好失败。
- 二次定位：游客令牌自动续期已经成功，但浏览器还保存着一个旧的正式登录令牌；请求头始终优先选取该令牌，所以新的游客令牌没有真正用于后续请求。
- 修复：遇到 HTTP 401 或业务码 `1101` 时先尝试刷新正式令牌；刷新失败后，仅在偏好、路线和反馈等游客业务接口清理失效登录状态、创建匿名会话并重试一次。页面身份提示同时切换为临时游客。
- 验证：后端日志确认游客续期请求及重试 `PUT /api/preferences` 返回 200；前端生产构建通过。
- 状态：已完成。

### BUG-12 改线残留冲突、未按当前位置规划且路线时长固定

- 现象一：局部改线或整程重排完成后，结果中仍可能保留被事件影响的地点，却显示为改线成功。
- 现象二：改线继续使用创建行程时的旧偏好和起点，未读取用户刚更新的当前位置；候选点缺少稳定的距离排序，表现为随机改线。
- 现象三：路线点位数量固定，用户设置更长或更短的出发、结束时间后，仍按“半日路线”生成。
- 冲突修复：改线前读取当前会话的最新偏好；候选点统一排除所有生效事件影响点、已使用点和未受影响的保留点。改线求解结束后再次执行全部硬约束校验，只要仍有冲突就拒绝提交新版本并返回具体原因，不再伪装为成功。
- 当前位置修复：局部替换按“最新当前位置或前一未受影响节点 → 候选点 → 下一未受影响节点”的新增距离排序，并加入区域、兴趣和无障碍条件；整程重排从最新位置重新选择邻近区域点位。相同分数使用稳定点位代码排序，结果可复现。
- 时间窗修复：路线目标点位数改为由 `departure_time` 到 `latest_end_time` 的可用分钟数动态计算，范围为 1–8 个点，并确保包含全部必去点；当预计结束时间或步行上限冲突时，逐个移除非必去的末端点并重新求解，直至满足硬约束或明确报告无解。
- 前端文案：四语界面的“生成半日路线”改为“按偏好时间生成路线”，空状态同步说明路线依据偏好中的开始和结束时间生成。
- 自动化验证：后端 10 项测试全部通过，新增覆盖短/长时间窗点位数量变化、更新当前位置后的整程重排、冲突点彻底移除和首段起点更新；前端 Vite 56 模块生产构建通过；后端打包成功。
- 真实接口验证：`09:00–14:00` 生成 4 个点，`09:00–18:00` 生成 7 个点；模拟封锁 `P005` 后，局部改线与整程重排均返回 `feasible=true`、冲突数 0、残留 `P005` 为 false，首段均从最新的“氹仔当前位置”出发，整程重排首站区域为 `TAIPA`。
- 状态：已完成，等待用户验收。

### BUG-13 整程重排在必去点被事件封锁时失效

- 现场条件：运营端模拟事件一次封锁澳门半岛全部 20 个点位，用户必去点也位于封锁范围内。
- 根因：旧逻辑同时要求“移除事件封锁点”和“必去点绝对保留”，两个条件相互矛盾，因此后端拒绝提交重排结果，前端看起来像按钮失效。
- 修复：用户主动点击局部或整程改线时，安全事件命中的必去点仅在该次改线中临时挂起，从路线移除并返回明确警告；未受影响的必去点继续严格保留。
- 界面修复：安全挂起说明以黄色提示显示；改线业务错误移到路线状态和改线组件上方，不再隐藏在长行程底部。改线成功后若当前路线已不受事件影响，后续重复请求会明确提示无需再改线。
- 自动化验证：后端共 10 项测试通过，新增“必去点被封锁”回归用例；前端 56 模块生产构建通过。
- 真实接口验证：封锁澳门半岛 20 个点位，并把 `P005` 设为必去点；整程重排返回 `GLOBAL_REROUTE` 和 `feasible=true`，冲突数 0，封锁点残留数 0，路线转入氹仔并从最新位置出发，同时返回 1 条安全挂起警告。
- 状态：已完成，等待用户验收。
